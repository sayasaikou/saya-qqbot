## 一、结论先行

**可行。** 而且这是目前**唯一合规且稳定**的路 —— 微信那条路 2026-10-04 已经查证堵死（Gewechat 停止维护、WeChatFerry 归档、WeChatPadPro 转付费灰产）。

但有三条**硬约束**必须写在最前面，因为它们直接决定机器人能做什么、不能做什么：

| # | 约束 | 实际影响 |
| --- | --- | --- |
| 1 | **群聊里只有被 @ 才会收到消息**（事件 `GROUP_AT_MESSAGE_CREATE`）；被动回复窗口 **5 分钟 / 5 次** | 机器人**不能**自主决定"什么时候插话"。想做主动发言只能走主动消息，而**用户可以在客户端关掉**「允许主动发送」，关了就一律失败 |
| 2 | **单聊被动窗口 60 分钟 / 4 次**（比群聊宽得多） | 私聊体验会明显好于群聊；重要功能建议引导到单聊 |
| 3 | **发消息要求 WebSocket 保持在线** | 必须长连接，不能纯 Webhook 无状态。云服务器 24 小时在线正好满足 |

待遇：主动消息每日上限 **1000 条/用户**、**1000 条/群**；个人认证下的频控 单聊 10/qps、群聊 60/qpm。

## 三、需求逐条对照

| 你的要求 | 能不能做到 | 怎么做 / 卡在哪 |
| --- | --- | --- |
| **1. 有我的人格，但不带我的记忆** | ✅ 能做到，且**要做的正是"物理隔离"** | 见 §4.1。人格规格（`PERSONA_SPEC`）本身与环境无关，可以整个搬；**`关系记忆.md` 与全局 `AGENTS.md` 的饲主档案必须排除** —— 那是"我们之间"的东西，不能给外人看 |
| **2. 按 QQ 号独立存聊天记录，跨时间跨群聊是同一个人** | ✅ 完全可行 | 见 §4.2。**关键设计：主键是 QQ 号，不是群号**。群聊只是"这段对话发生在哪"，不是身份的一部分 |

| **4. DSH 跑云端 24 小时，同一人格 + 共享仓库** | ⚠️ 可行，但**有个架构选择要你定** | 见 §5。是"云端跑完整 DSH"还是"只跑轻量消息服务"，成本与灵活度差别很大 |
| **5. 表情包** | ✅ 可行（官方支持富媒体） | 见 §4.4。要两样：**图库（图 + 文字标注索引）** ＋ **发送前的图转存** |

## 四、架构设计

### 4.1 人格的剥离（这是最需要小心的一步）

现在的人格是**三层**，必须按层处理，不能整个搬：

```
① PERSONA_SPEC（行为规格）        ← 整个搬。它讲的是"怎么说话"，与环境无关
   └─ 来源：plugins\dafatfish\index.js 里的常量

② 全局 AGENTS.md                  ← ❌ 不能整搬！
   ├─ 「沟通偏好 / 两档模式 / 人物设定」  → 可以挑出来放进云端版本
   └─ 「饲主档案 / 心理状态 / 那封信 / 学校 / 设备 / 家庭」 → 一条都不能给出去

③ persona\关系记忆.md             ← ❌ 绝不外流
   └─ 这是"我们之间"那层。云端不放、仓库不放、任何形式都不放
```

**推荐做法**：云端用一个**独立的精简 AGENTS.md**（只含 ① 与 ② 的公开部分），放在独立仓库里；本机的两份档案**一个字都不动**。这样两边天然隔离，不存在"忘了删一段"的风险。

> ⚠️ 一个必须提醒的点：云端那个 DSH 跑起来后，**它是能被 QQ 用户对话诱导的**。所以云端人格文件里**不能留任何本机细节**（路径、用户名、你的作息、学校、战队、设备型号）——不是"尽量不主动说"，而是"文件里根本没有"。这条比什么都重要。

### 4.2 数据模型（按 QQ 号，不按群）

```
data/
├── users/
│   └── <qq号>/
│       ├── profile.json      # 昵称、首次出现时间、最后活跃、所在群列表
│       ├── history.jsonl     # 完整聊天记录，追加式（append-only）
│       └── memory.md         # 这个人的长期记忆（由云端 dsh 自己维护）
└── groups/
    └── <群号>.json           # 群成员 QQ 号列表 + 群级设置
```

`history.jsonl` 每行一条：

```json
{"ts":"2026-10-05T11:46:00+08:00","scene":"group","group":"123456","role":"user","text":"...","meme":"熊猫头·无语"}
```

**为什么用 jsonl 而不是 SQLite 单库**：jsonl 是纯文本、可 diff、可直接 git 提交、冲突好处理；单库文件二进制、git 不适合。规模上你说了"不会给几千个人用"——**每人每天 100 条 × 1000 人 × 一年 ≈ 36 MB 纯文本**，git 完全扛得住。

**跨群聊 = 同一个人**：因为主键是 QQ 号。群里说话时，云端把 `<qq号>/history.jsonl` 的最近 N 条（不论来自哪个群）一起喂给模型 ⇒ 他在 A 群说过的事，B 群也记得。

### 4.3 云端仓库与同步

- **新建一个私有仓库**（例如 `saya-qqbot`），存：人格文件、消息服务代码、`data/`。
- **本机**：`git clone` 下来，随时读、改、提交 —— 想手改某人的记忆，直接改 `users/<qq>/memory.md` 推上去。
- **云端**：定时 `git pull` 拉人格与设置的改动、`git commit && push` 上报聊天记录。
  - ⚠️ **高频提交会有问题**（每次消息都 commit 会把历史撑爆）⇒ 策略：**每 N 分钟或每 M 条消息提交一次**，或只在会话结束时提交。
  - ⚠️ 凭据（QQ AppID/Secret、模型 API Key）**绝不进仓库**，走云端环境变量（这条我们已经在 `sync.ps1` 里做过拦截）。
- **备份**：仓库本身就是备份；再叠一层云端每日快照（便宜、省心）。

### 4.4 表情包

要两样东西，缺一不可：

1. **图库本体**（图片文件 + 文字标注）—— 可以直接复用本机那 269 张（`meme-packs\`），也可以只用其中一部分。**文字标注是关键**：模型不需要"看懂"图，它只需要按 `[表情: 描述]` 挑一个描述，由服务层把描述映射成图片。
2. **图转存** —— QQ 官方**不接受直接发图片 URL**，必须先上传拿 `file_info` 再发 `msg_type=7`。所以流程是：模型输出描述 → 服务层在库中匹配 → 上传图片 → 发送。`file_info` 有 ttl，缓存起来能省调用。

> 线上还要考虑审核：官方有 `MESSAGE_AUDIT` 审核事件。第一版建议**保守配置表情包**（只用合规的、去掉带梗的敏感图）。

## 五、⭐ 需要你定的第一个大选择：云端跑什么

这是整个项目**成本与灵活度差别最大**的一个决定，两条路：

### 方案 A：云端跑完整 DSH

```
QQ → 消息服务（Node）→ 云端 DSH 实例（dsh --headless）→ LLM
                              ↓
                    人格插件 + data/ 仓库
```

- ✅ **人格与插件生态 1:1 复用**（同一个 `dafatfish` 插件、同一份规格、同一套表情包插件）
- ✅ 你说的"新的 dsh 聊天机器人"**字面成立**
- ❌ 资源重（Electron 那套跑不了，得用 CLI headless）；**冷启动慢**，而群聊被动回复窗口只有 5 分钟
- ❌ 多人高并发时"一个会话等另一个"，需要自己做会话池
- ❌ 每次调用都要过一次 DSH 的系统提示 + 插件注入，**token 成本高**

### 方案 B：轻量消息服务（推荐）

```
QQ → 消息服务（Node）→ LLM API      ← 人格由文件注入，历史由 SQLite/jsonl 管理
                    ↓
            data/ 仓库（git 同步）
```

- ✅ 轻、快（响应 1~3 秒）、并发好做
- ✅ **token 花在刀刃上**（只注入人格 + 该用户的最近历史，不注入整套工具说明）
- ✅ 数据模型完全按你的要求（按 QQ 号）
- ❌ 人格要"搬"而不是"复用"（规格是文本，搬过去就行，但要维护两处）
- ❌ 用不上 DSH 的插件生态（表情包、识图这些要单独实现）

### 方案 C：A + B 混合（本鱼倾向）

**主链路走 B**（快、省、好维护），**但保留一个云端 DSH 作为"重活"后端** —— 需要查资料、跑代码、生图这类任务时，消息服务把请求转给云端 DSH，结果回传。日常闲聊走轻量链路。

> 本鱼的建议：**先做 B 跑通**（一到两天能出可用版本），**A/C 作为第二阶段**。理由：B 能立刻验证"人格搬过去像不像"，而这才是这件事的核心风险；架构可以后加，人格不像就得推倒重来。

## 六、成本估算

| 项 | 估算 | 说明 |
| --- | --- | --- |
| 云服务器 | **38 ~ 199 元/年** | 阿里云轻量 2核2G/2核4G 活动价。**2核2G 够跑方案 B**；跑方案 A 建议 2核4G |
| 域名 | **0**（可选） | 已有 `sayanodsh.com`，可加子域；WebSocket 模式其实不需要公网域名 |
| 模型 API | **按量，需实测** | 见下 |
| 仓库 | **0** | 私有 git 仓库免费 |
| QQ 开放平台 | **0** | 个人认证免费 |

**API 成本的关键变量**（本鱼不敢瞎报，得看你选哪条路）：

- **方案 B**：每次对话 ≈ 人格 1.5k + 历史 1k + 回复 0.5k ≈ **3k token/轮**。DeepSeek 按现价约几厘/轮 ⇒ **日常自用每月几元到几十元**（取决于多少人聊）。
- **方案 A**：每轮还要叠 DSH 的系统提示与工具说明（本机实测这类开销不小）⇒ 同等人次下**可能是 B 的 3~10 倍**。
- ⚠️ **真正的风险不是单价，是"有人刷"**。必须做每用户限流 + 每日 token 上限，否则一个群拉满就能把这个月的额度烧完。**这条本鱼会在设计里写成硬约束。**

## 七、风险与坑（提前说清）

| 风险 | 应对 |
| --- | --- |
| **人格泄露本机细节** | 云端人格文件物理隔离（§4.1）。这是**一号风险** |
| **被人诱导"越狱"** | 内置护栏 + 云端不存任何凭据；出格直接结束对话 |
| **刷量烧钱** | 每用户限流 + 每日 token 上限 + 超限静默降级 |
| **群聊窗口只有 5 分钟** | 长任务（查资料、生图）改成"先回一句在处理 → 完成后用主动消息推"（⚠️ 用户可能关了主动消息，要有兜底文案） |
| **`msg_id` 重复推送** | 必须做去重，否则同一句话回两遍 |
| **QQ 审核** | 第一版保守：不涉政、不擦边、表情包精选；保留 `MESSAGE_AUDIT` 事件处理 |
| **云端断线** | 官方要求 WebSocket 保活 ⇒ 做进程守护 + 掉线自动重连 + 掉线告警 |
| **数据合规** | 聊天记录属个人信息，仓库必须私有、凭据不进仓库、可一键删除某个 QQ 号的全部数据（**建议做成命令**） |

### 10.2 可参考的架构：官方团队自己的分层

`openclaw-qqbot` 的 `src/` 结构（腾讯官方团队自研，MIT）：

```
adapter/      协议适配（把 QQ 事件转成内部格式）
dispatch/     消息分发（决定这条消息该走哪条链路）
middleware/   访问控制、附件处理、策略注入
outbound/     出站流水线（TTS → 媒体 → 文本防抖 → 流式控制 → 回复限速）
gateway/      连接管理（WebSocket 保活 / 重连）
commands/     斜杠指令
features/     业务特性
```

这套分层正好覆盖你要的东西 —— **`middleware` 放限流与白名单、`outbound` 放表情包发送与防抖、`dispatch` 放"要不要回这条消息"的判断**。

### 10.3 ⭐ 群聊不只有"被 @ 才活"这一条路

官方 FAQ 原文（腾讯自己写的）：

> **接收全量消息能力**：当群主设定允许该机器人接收群内全部消息时，机器人可接收到群内所有成员在群内的发言消息。
> **主动推送消息能力**：机器人主动在群聊内发言，如定时任务推送等。
> **机器人撤回成员消息能力**：当机器人被群主设置为群管理员时，可撤回成员发送的消息。

并且 `openclaw-qqbot` 已经实现了**按群配置触发规则的优先级链**：`具体群 > 通配符 * > 账户级 > 默认值`，还有运行时可切换的 `/bot-group-allways` 指令。

⇒ 所以「小灰条提示机器人不在线」那种问题是有解的，而且**三种模式可以按群分别设**：

| 模式 | 体验 | 成本 | 适合 |
| --- | --- | --- | --- |
| 只在被 @ 时回 | 像工具 | 低 | 热闹的大群 |
| 听全量但自己判断要不要接话 | 像真人 | **高**（消息量翻几十倍） | 自己的小群 |
| 按群分别设 | 可调 | 可控 | **推荐起步方式** |

### 10.4 人格剥离的实测数据（这是最重要的一节）

本鱼把能搬的那一层（`PERSONA_SPEC`，**7,708 字符**）拿真实内容跑了一遍检查，结果：

| 层 | 体量 | 实测结论 |
| --- | --- | --- |
| ① `PERSONA_SPEC` | 7,708 字符 | ⚠️ **可以搬，但必须改 11 处**（见下） |
| ② 全局 `AGENTS.md` | **67,126 字符** | ❌ **绝不能整份搬** —— 实测含「一、关于我 / 工作方式与自我认知 / 抑郁 / 桂林信息科技学院 / 宿舍作息 / Vector 16」等段落，**每一段都会直接暴露你是谁**。只能挑出「沟通偏好」那几节 |
| ③ `persona\关系记忆.md` | 39,643 字节 | ❌ **绝不外流**。这是"我们之间"那层 |

**① 层的问题分两类，共 11 处 ERROR：**

- **2 处隐私泄漏**：规格里**硬编码了 `<你的用户名>/...` 的路径**（视觉工具的说明那段）⇒ 直接泄漏用户名。
- **9 处"一对一写法"**：「饲主」出现 **10 次**。这份规格是**为"只有一个对话对象"写的** —— 搬到多人群聊会**人称全乱**：机器人会管所有人叫"饲主"、把不同 QQ 号的人当成同一个人。

**另有 41 处 WARN 需要你逐条决定**（不是错，是"搬过去要重新拍板"）：

- 「本鱼」这个自称要不要在云端沿用（**建议沿用**，那是人格的一部分）
- 「两档模式 / 工位档 / 伙伴档」「上工 / 歇会儿」这类**只对熟人才成立的约定**，对陌生人未必适用
- 「战队 / 学业 / 超频」这类举例 —— 单独看没事，但**合起来可能反推出你是谁**
- 视觉工具那条链（`eye.py` / `vision-tools`）—— 云端多半用不上，删掉更干净

**本鱼已经把这个判断做成了可执行的检查器**：`tools\check-cloud-persona.py`
每次改完云端人格文件跑一次，它逐行报出 ERROR / WARN，退出码 `0` 通过 / `2` 不能上线 / `3` 有警告。**这条能防止将来手滑把私人内容推上云。**

> 顺带一个教训（本鱼当场踩的）：这个检查器第一版**自己崩在 Windows 控制台的 GBK 编码上**（打印 ⚠️ 时抛 `UnicodeEncodeError`）—— 而这正是本鱼**今天上午刚写进公开仓文档的那个坑**，同一个下午又踩了一次。已修。

## 十一、⭐ 重大发现：腾讯官方已经做了「DSH 接 QQ」

**`tencent-connect/dsh-qqbot`** —— 官方插件，描述原文就是「让 QQ Bot 接入 DeepSeek Harness（dsh）的官方插件」。

| 项 | 实测值 |
| --- | --- |
| 仓库 | 119 star ｜ TypeScript ｜ MIT ｜ 创建 2026-08-14 ｜ 最后 push **2026-09-08** ｜ 19 个 open issue |
| npm | `@tencent-connect/dsh-qqbot` **v0.5.0**（5 个版本，首发 2026-08-14）｜ 周下载约 949 |
| 依赖 | peerDeps 指向 `@deepseek-ai/cordis` + `dsh-agent` / `dsh-llm` / `dsh-session` / `dsh-user-approval` ⇒ **确实跑在完整 DSH 上** |

### 11.1 它已经内建了什么（对照你的五条需求）

| 你的需求 | 它现成的实现 |
| --- | --- |
| ① 人格、但不带记忆 | 它**读 `cwd` 的人格文件**；用**独立 profile**（`--profile qqbot`）= **独立家目录 = 独立会话存储** ⇒ **天然隔离，碰不到本机记忆**。另有两个专用参数：`groupPrompt` / `directPrompt` 可**额外注入群聊/私聊专属 system prompt** |
| ② 按 QQ 号独立存、跨群聊同一个人 | sessionKey = `qqbot:${appId}:${scope}:${peerId}`（SHA-256 派生，**重启可恢复**）；**每个 peer 一个独立 Agent** ⇒ 隔离天然成立。⚠️ **但"跨群聊是同一个人"它不自动做** —— `peerId` 是"群"或"人"，同一人在两个群是两个 Agent。这一条要我们自己在外部补 |
| ③ 云端仓库、本机可读写 | 它不管这块，**要我们自己做**（本来就是独立需求） |
| ④ 24 小时云端跑 | ✅ 支持；`/bot-status`、闲置回收、`maxQueue` 都在 |
| ⑤ 表情包 | ⚠️ **部分**：它有 `qqbot_send_file` 能发本地文件（带路径白名单），但**没有"按描述挑图"的图库逻辑** —— 那层要我们写 |

**另外白送的**：斜杠命令（`/new` `/compact` `/model` `/stop` `/bot-help` 等 9 个）、**流式输出**（私聊，群聊自动关）、**图片视觉理解**（`qqbot_describe_image`）、**问答内联按钮**（`ask_user_question` 单选/多选）、**审批通道**（`approval/request` 允许/拒绝按钮）、Markdown 感知切分、`requireMention` 群聊@开关。

### 11.2 ⚠️ 两个必须先处理的坑

1. **默认 `model` 写的是 `deepseek-chat`，而那个模型 2026-07-24 已停用** ⇒ 照默认配置启动，**第一句话就会报错**。必须显式改成 `deepseek-flash`。
2. **peerDeps 要求 `>=0.1.0-rc.6` 的 DSH 核心包**；本机 npm 上 latest 是 `0.2.0-rc.2`（alpha 有 `0.2.1-alpha.1`）。**版本兼容性没实测**，动手第一步就得验。

### 11.3 路线修正（本鱼改了建议）

原计划是「先自建轻量服务（方案 B）」。现在多了一条更省事的路，两者不冲突，**应该串起来**：

| 阶段 | 做什么 | 产出 | 代价 |
| --- | --- | --- | --- |
| **第 0 步（新增）** | **本机**装官方 `dsh-qqbot` 到独立 profile，改 `model`，扫码绑定 | **最快看到"人格搬过去像不像"** —— 这是整个项目最大的未知数 | 0 元（只花 API 费）＋ **一张实名认证**（只有你能办） |
| **第 1 步** | 按第 0 步的观感迭代人格文件（用 `tools\check-cloud-persona.py` 把关） | 一份**可复用的干净人格** | 本鱼的活 |
| **第 2 步** | 上云：决定是**直接跑 dsh-qqbot**（省事、吃资源）还是**自建轻量服务**（省资源、要写代码） | 24 小时在线 | 服务器 38~199 元/年 |
| **第 3 步** | 补上它没有的三块：**跨群聊记忆 + 表情包图库 + 云端仓库同步** | 你要的完整形态 | 本鱼的活 |

**为什么先做第 0 步**：它把"人格像不像"这个**最大风险**用最低成本验证掉。人格不像，后面全白做；人格像了，剩下的都是工程量。

### 11.4 一条硬门槛：IP 白名单（动手前必须知道）

官方文档写明：**新增机器人默认启用 IP 白名单，只有白名单内的 IP 才能连 WebSocket、才能调 OpenAPI；不填 IP 白名单不能提审上线。**

⇒ 两个后果：
1. **云服务器必须是固定公网 IP**（轻量服务器默认给固定 IP ✅，动态 IP 的方案不可用）；
2. 本机（第 0 步）与云端（第 2 步）**IP 不同** ⇒ 切换时要**在白名单里加新 IP**，否则连不上。

### 11.5 沿用的、不受影响的技术结论

- **官方 Node SDK 用 `@tencent-connect/qqbot-nodejs`**（现役），**不要**用官方文档里挂的 `bot-node-sdk`（2022 年停更）。⚠️ 但新 SDK 也有风险：仓库开源后**只有 1 个 commit、两个月零提交**、5 个 issue 无人回复。
- **沙箱是独立域名** `sandbox.api.sgroup.qq.com`（正式是 `api.sgroup.qq.com`），**不是开关参数**；沙箱群/账号要在管理端单独配。
- **`srv_send_msg=true` 会占用主动消息频次** ⇒ 想让图片走**被动回复**，必须 `srv_send_msg=false` 拿 `file_info` 再单独带 `msg_id` 发。**这是发图最容易踩的坑。**
- **WebSocket 重连**：4009 → 可 RESUME；4006/4007 → 必须重新 IDENTIFY；4914/4915 → 不许连。
- ⚠️ **一处官方文档自相矛盾**：`GROUP_MESSAGE_CREATE` 在「消息收发」页列了，但 intents 页的清单里**没有它**。动手前读官方 SDK 的 `src/protocol/gateway/constants.ts` 定案（本鱼没实测）。
